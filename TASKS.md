## PR 12 — Meta-folders via drop-anywhere-except-icon

New feature: any block/file/module/folder can become the organizational parent of any other bucket item, entirely independent of disk location — completing meta-organization alongside the existing on-disk-independent bucket/view model. Grilled with Dan directly; the original "drop on the right side of the row" idea was simplified during grilling to an icon/non-icon split.

- [x] **Data model:** every `ViewNode` type (block/file/module/folder) gains optional `children`/`collapsed` fields, unifying with how Folder nodes already work — a promoted node keeps its own identity/content (clicking it still opens the file/interface note, etc.), it just additionally gains a chevron + children area. This is what distinguishes it from a plain Folder, which stays purely organizational with no content of its own. Turned out `ViewNode` already had these fields untyped-restricted (a runtime convention, not a type-level one) and most of `views.ts`'s tree-walking (`findNode`, `rewriteTree`, `isSameOrDescendant`) already recursed into any node's `children` generically — the only real gate was `moveNode`'s explicit `newParent.node.type !== "meta"` check, relaxed to accept any found node.
- [x] **Modules:** the icon is reserved exclusively for the existing real disk-move interactions — the plain drop-confirm (PR 8) *and* the dwell-timer-opens-modal flow (PR 9, moved here from whole-row per this PR's grilling). Dropping anywhere else on a module's row (label included) creates a meta-nest relationship instead — organizational only, no disk move. Verified live via CDP: dropping a file directly on a module's icon still opens the "Add to module" confirm dialog; dropping the same file on the module's label instead nests it as a meta-child with no dialog.
- [x] **Files/blocks/folders:** no disk-move capability exists for these in the bucket, so the entire row is eligible as a meta-nest drop target — no icon carve-out needed. Verified live: file-onto-file nesting, and cross-type module-onto-file nesting, both land correctly.
- [x] A node shows no chevron until it actually gains its first child — no pre-emptive chevrons on every row. Verified live both directions: nesting a child in grows the parent's chevron in; removing its only child (un-nest or "Remove from view" promoting the child up) makes the chevron disappear again.
- [x] Un-nesting: dragging a nested child out to the bucket root, or onto another row's non-icon zone, re-parents/un-nests it via the existing reorder mechanics — no new UI needed. Verified live: dragging a nested child back onto the bucket-root drop zone returns it to a top-level sibling.
- [x] Fold/unfold for these new chevrons reuses the existing `grid-template-rows` animation technique — extracted the whole meta-folder fold/unfold block (filter-driven auto-reveal, chevron icon, animated wrapper, optimistic-local-state click handler) into a new shared `renderFoldableChildren` method used by both meta and unit branches, instead of duplicating it a second time, so the two can't drift out of sync the way duplicated logic has caused real bugs elsewhere in this build.
- [x] Edge case: nesting a module under a file (and every other cross-type combination) — verified live (module-under-file); the mechanism is generic (any found node becomes `parentId` regardless of type) so every other combination goes through the identical code path.
- [x] Edge case: deeply nested chains (3+ levels) — verified live: a 3-level file→module→file chain, correct `paddingLeft` at every depth, "Collapse all" correctly collapsed both non-leaf levels.
- [x] Edge case: dragging a node onto itself, or onto one of its own descendants — must be prevented (cycle prevention) — verified live: dragging a parent onto its own just-nested child left the tree structurally unchanged (the pre-existing `isSameOrDescendant` check in `moveNode`, already generic across node types, needed no changes).
- [x] Edge case: a module's icon-only disk-move zone coexists correctly with its now-narrower meta-nest zone — verify dropping on the label specifically nests rather than files-into-module — verified live (see the Modules bullet above); icon and row now have fully separate drop-zone listeners with `stopPropagation()` between them so a drag never triggers both.
- [ ] **Known gap, flagged by review (A15), deliberately not fixed here:** dropping one module directly onto *another module's icon specifically* is a silent no-op — it correctly fails the disk-move check (`ref.kind !== "folder"`, since a folder can't be filed into another folder this way), but the icon's own `stopPropagation()` also blocks the row-level meta-nest fallback from ever seeing that drop. Narrow (only the icon's own small hit area, missing it by a pixel falls through to meta-nest correctly), easy workaround (drop on the label instead), and the reviewer explicitly framed this as not worth fixing now. Left as a named, deliberate gap rather than silently missed.

**Two real, pre-existing bugs found and fixed while implementing this** (not introduced by this PR, but made either newly reachable or newly consequential by it — logged in `docs/decisions.md`):
- [x] `unplaceUnit` ("Remove from view" / Delete key) discarded a removed unit's children outright instead of promoting them up a level the way `deleteMetaFolder` already does for meta folders — harmless before this PR (units never had children to lose), silently data-destructive after. Fixed to match `deleteMetaFolder`'s pattern; verified live (Remove from view on a unit with a nested child correctly promotes the child to where the parent used to sit).
- [x] `handleDrop`'s reparent path for an existing tree node (`payload.kind === "node"`) routed through `placeUnit`, which builds a *brand-new* node object with `children: []` — discarding the dragged node's real children/collapsed state on every reparent, and never actually working at all for a dragged *meta* folder (`placeUnit` only matches by `UnitRef`, which metas don't have, so a meta-folder drag silently produced a garbage-ref phantom node instead of moving the real one). Fixed by calling `moveNode` directly for this case, which reparents the real node object in place. Also fixed `pathToRef` (view.ts, used for the "placed in…" row tooltip) and `collapseAll`, both of which only recursed into `meta`-type children before this PR — a unit nested under another unit would have silently reported as "not placed" and never collapsed via "Collapse all".

**Testing note:** all of the above verified live via the Chrome DevTools Protocol against `desktop-atlas-modules`, using synthetic `DragEvent`s with a real `DataTransfer` (`dragstart`/`dragover`/`drop`/`dragend` dispatched directly in the page's own JS context) rather than VNC mouse simulation — this plugin's drag logic is driven entirely by these DOM-level events (`dragPayload` is set/read by the app's own listeners, not by native OS drag-and-drop file-transfer semantics), so this exercises the real code paths, not just a proxy for them.

New feature: place the same unit in multiple spots in a view's tree without duplicating it on disk. Grilled with Dan directly — his first proposed naming scheme (numbered suffixes) turned out to have no real answer to "how do two sibling nodes pointing at the same disk path get different names without a fake 'meta name'", so the scheme was dropped entirely in favor of allowing duplicate labels outright.

- [x] **No naming/numbering logic** — the duplicate displays with the identical label as the original; two (or more) siblings with the same visible name is expected and fine — verified live throughout, including three simultaneous "1 Point Everyday" rows after a couple of rounds of duplication.
- [x] If the duplicated item has children (via PR 12's meta-nesting), the **entire child subtree is recursively cloned** too — new node IDs throughout, each still referencing the same underlying units as its original counterpart — and placed under the new duplicate — verified live: duplicating a parent-with-child produced a second parent row immediately followed by its own cloned child at the correct depth.

- [x] Technical check (not a user-facing AC): grep the codebase for any place that assumes one-`ViewNode`-per-unit-per-view uniqueness (e.g. a `Map`/`Set` keyed only by path) that would break once two sibling nodes can reference the same unit — fix if found. **Found two real gaps, both fixed** — see the "duplicate-aware fixes" note below.

- [x] Edge case: duplicating an item that is itself already a duplicate — clones again the same way, no special-casing — verified live: duplicating an already-duplicated row produced a third instance with no special handling needed, the recursive `cloneNode` doesn't know or care whether its input was itself a clone.
- [x] Edge case: duplicating a deeply-nested item — the clone is reinserted as a sibling at the **same nesting depth**, not promoted to root — verified live: duplicating a depth-1 nested unit produced a second depth-1 sibling under the same parent, not a root-level node.

**Duplicate-aware fixes found during the technical-check pass** (not user-facing ACs on their own, but real correctness gaps the duplication feature exposes — logged in `docs/decisions.md`):
- [x] `unplaceUnit` (backing "Remove from view", the Delete key, the missing-ghost "×" button, and drag-to-inbox-unplace) found the *first* matching ref anywhere in the tree and removed only that one — meaning right-clicking a *specific* duplicate's "Remove from view" could silently remove a *different* instance than the one the user was looking at. Verified live: removing one of two duplicate instances via its context menu left the other completely untouched.
- [x] `getPlacements`/`pathToRef` (the "placed in…" row tooltip) stopped at the first match per view, so a unit duplicated to two spots within the *same* view would only ever report one placement. Renamed to `allPathsToRef`, now collects every match in the subtree instead of returning early. Verified live via `plugin.viewsManager.getPlacements(...)` directly: two entries returned for the same view after duplicating a root-level unit once.
