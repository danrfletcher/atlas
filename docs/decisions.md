# Decisions

Judgement calls made during the build, the alternative considered, and why. Newest first.

## PR 9: "Module" / "Folder" terminology swap — UI text only, internal code identifiers untouched

**Decision:** confirmed directly with Dan before starting (not guessed): every physical folder-unit is now called **"Module"** in user-facing text everywhere (buttons, tooltips, dialogs, context menus, settings, README), and what was previously "meta folder" drops the "meta" qualifier and is now just **"Folder"** — the word became free to reuse specifically because the physical-folder concept moved to "Module". This resolved what initially looked like a contradictory toolbar spec ("Add Module" *and* "Add Folder" as two separate buttons) — they're genuinely two different buttons once you know the swap: "Add Module" creates a physical folder on disk (renamed from "Add Folder"), "Add Folder" creates a bucket-arrangement label (renamed from "Add meta folder").

**Scope: UI text only, not code.** Internal identifiers — the `ViewNode.type: "meta"` discriminant, function names (`addMetaFolder`, `renameMetaFolder`, `showMetaFolderMenu`), CSS classes (`atlas-meta-children`) — are staying as they are. Renaming those too would be a large, purely mechanical, cosmetic-only pass across most of `explorer-view.ts` and `views.ts` with real risk of introducing bugs (variable shadowing, missed call sites, CSS selector drift) for zero behavior change and no user ever seeing the difference. The cost/benefit doesn't clear the bar the way the earlier F11 perf fixes or F8 drag fixes did — those changed what the plugin actually does; this only changes what a word says. Logged explicitly here so the deliberate code/UI split reads as a choice, not an inconsistency, if a future pass ever touches this code and notices the words don't match.

## PR 9: hover-during-drag-to-open-modal — accepted as best-effort, same risk tier as all drag work

**Decision:** issue 2's "hold a drag over a module without dropping to open its Contents modal, then drop into any nested location inside it" is being built to spec, at the same best-effort/unverified standard as every other drag-and-drop feature in this plugin — confirmed with Dan directly rather than assumed, after flagging that this is genuinely the most technically novel piece in this batch (a `Modal` opening *while* a native HTML5 drag is still active, itself becoming a live multi-target drop zone for that same in-flight drag) and that it inherits the same fundamental limitation as everything drag-related: no working synthetic HTML5 drag-and-drop in this container, so it can't be end-to-end verified here regardless of how carefully it's built. Two options to de-risk it (a simpler fallback shipped alongside it, or deferring it entirely to a follow-up) were offered and explicitly not chosen.

**Why build it anyway rather than pre-emptively simplify:** Obsidian's `Modal` renders as an in-window DOM overlay (`.modal-container`), not a separate OS-level window, so there's no structural reason a `dragover`/`drop` listener on an element inside it wouldn't fire normally — the risk is more about dwell-timer UX feel and edge-case handling (drag released early, dragged elsewhere, modal closed mid-drag) than about the browser refusing to cooperate. Reasoned through each edge case named in `TASKS.md` rather than only building the happy path, which is the most that can be done without a real drag input device.

## F8: real bug in the fold/unfold animation — rapid double-click got stuck instead of toggling back

**Decision:** caught in review (A11), not live testing — the chevron click handler computed `const collapsing = !node.collapsed`, reading the *data-model's* collapsed flag directly. That flag only actually updates once the deliberately-delayed (`META_COLLAPSE_TRANSITION_MS` = 160ms) `setNodeCollapsed` call runs and the resulting full re-render lands. A second click inside that 160ms window read the exact same unchanged `node.collapsed` value as the first click, so `collapsing` computed the identical direction both times — the row visibly got stuck (re-applying "collapse" twice, say, instead of collapse-then-expand) rather than alternating each click the way every other toggle in the UI does.

**Fix:** track the collapsed/expanded state as a local `let localCollapsed` variable scoped to that row's own click handler (initialized from `node.collapsed`, but from then on only ever updated by flipping its own prior value on each click — never re-read from the data model until the eventual full re-render replaces the whole closure anyway), and clear/reschedule the pending `setNodeCollapsed` timeout on every click rather than letting multiple stacked timeouts fire independently. Both were needed: the local variable fixes the "reads stale state" bug directly; the timeout cancellation means only the *last* click in a rapid burst ever gets persisted, so a quick collapse→expand→collapse doesn't also briefly persist and re-render the intermediate "expand" state before landing on the final one.

**Verified live** (this one doesn't need drag input, just clicks): a rapid two-click burst on the same chevron now correctly returns to the starting icon/state instead of getting stuck: from collapsed, two quick clicks land back on collapsed (confirmed via zoomed screenshots of the chevron icon before/after); a single click still toggles normally. No console errors either state.

## F8: "add to module" — the one deliberate disk-mutating exception, and why it doesn't force-promote

**Decision:** dropping a file or block directly onto a folder-unit row now offers (via a toggleable `ConfirmModal`) to physically move the underlying file into that folder on disk via `fileManager.renameFile` — the single exception, anywhere in this plugin, to "Atlas never touches disk for arrangement." Requested directly by Dan during his own first hands-on drag-and-drop pass (the one thing this build's container could never exercise itself), not something built speculatively.

**Confirmed before writing any code, not guessed:** since this cuts directly against a rule verified by grep in every single PR review this whole build, I asked two clarifying questions rather than assume: (1) does confirming actually move the file, or something non-disk-touching? (2) does the settings toggle gate the confirmation only, or the whole feature? Answers: yes, physically move it, but only keep it as a distinct, addressable Atlas unit if it *already* has real backlinks from outside the module — no forced manual promotion — and the toggle controls only whether the confirmation dialog appears, not whether the move happens at all.

**Why no forced promotion is the right implementation, not just the requested one:** it's the only choice consistent with the rest of the model. A promoted-file unit is defined everywhere else in this codebase by having a real inbound link from outside its top-level folder — manufacturing a promotion here (the way the F3 "promote an internal" drag path deliberately does, a different, existing, unrelated mechanism this doesn't touch) would make "add to module" secretly behave like promotion via a completely different, disk-mutating gesture. Letting the *existing* link-graph recompute decide is not just simpler, it's the only version where a file's promoted status always means the same thing regardless of how it got there.

**How it actually resolves without new promotion logic:** `fileManager.renameFile` fires Obsidian's normal `rename` event, which this plugin already wires end-to-end — `viewsManager.onVaultRename` rewrites any existing bucket placement's ref to the new path, and (once Obsidian's own metadataCache re-settles, since other files' link text needs to catch up to the move first) `unitIndex`'s ordinary `computePromotions()` naturally reclassifies the file as `promoted-file` if a real backlink survived the move. No manual-promotion call was added. A one-time `metadataCache.on("resolved")` listener (registered at drop time, unsubscribing itself on first fire) checks after that settling whether the file is still a recognized unit; if not, that ref is proactively unplaced rather than left rendering as a confusing "(missing)" ghost caused by the user's own deliberate action (as opposed to the F9 missing-ref case, which is specifically about *unexpected* external changes and correctly stays visible-and-recoverable).

**Cleanup scope, corrected per review (A11):** the first version only unplaced the ref from whichever single view the drag originated in, leaving stale ghosts in any *other* view that also happened to have it placed. Caught in review, and the fix is a real scope correction, not a style nit: the file moved on disk for the whole vault, not "within" whichever view happened to be on screen during the drag, so losing unit status is a vault-wide fact — the same way `onVaultRename`'s own ref-rewriting already treats a path change as cross-view, not scoped to one view's context. Now iterates every view and unplaces the (idempotent, no-op-if-absent) ref from each.

**Scoped to file/block payloads only:** dropping one folder-unit onto another falls back to the existing sibling-insert behavior untouched — moving an entire folder's contents and internals wholesale is a materially bigger operation than what was asked, and not attempted here.

**What's unverified:** everything drag-related in this build has the same ceiling — no working synthetic HTML5 drag-and-drop in this container. This feature additionally needs a real backlink scenario to exercise both outcomes (promoted vs. not), which is even less reachable without live testing than a plain placement drag. Confirmed only that the code path is reachable and type-checks, and reasoned through the event-ordering (rename-triggered `viewsManager`/`unitIndex` listeners are registered before this feature's own listener, so `getUnits()` reflects the settled state by the time it's checked) rather than assuming it.

## F8: bucket-root drop target was often unreachable, and meta-folder icons were 4px misaligned — both real bugs from Dan's live testing

**Decision (drop target):** `makeDropZone`'s `bucket-root` registration moved from `.atlas-node-list` (a div whose height hugs its content in normal block flow) to the whole bucket section container. Once the list had a few rows, there was almost no empty space left within the list div itself to register a drop on — a drop landing just past the last row missed every registered target entirely, landing on the un-instrumented parent instead. Any specific row still wins first via its own handler's `stopPropagation`, so this only widens the *fallback* target, it doesn't change what a drop onto an existing row does. Added 16px of trailing padding to the list too, so there's always a visually obvious strip of empty space to aim for, not just a technically-reachable-but-invisible one.

**Decision (icon alignment):** traced the exact pixel math rather than eyeballing a fix — a meta row's icon sits `.atlas-chevron`'s width (14px) + `.atlas-row`'s `gap` (6px) = 20px past the row's padding-left edge; a plain unit row has no chevron, so its own compensating offset needs to equal that same 20px to land in the same place. It was 16, four pixels short — exactly the "sits a few pixels right" Dan described. Fixed by correcting the constant (`UNIT_ROW_CHEVRON_OFFSET = 20`) rather than adding an ad-hoc margin, so it stays anchored to the actual chevron/gap values instead of drifting out of sync with them again.

**Decision (fold/unfold animation):** added a reveal transition for meta-folder collapse/expand, matching Obsidian's native file-tree feel, using the `grid-template-rows: 1fr → 0fr` technique — the standard CSS-only way to animate to/from an implicit `auto` height without JS-measuring `scrollHeight`. This required a real structural change: meta-folder children now always render into a dedicated `.atlas-meta-children` wrapper (previously they were only rendered into the DOM at all when expanded, as flat indented siblings of everything else — there was no per-folder element to animate). The chevron click now does two things in sequence rather than one: it toggles the wrapper's CSS class immediately (for the animation to actually play), and only *then*, delayed by the transition's own duration (`META_COLLAPSE_TRANSITION_MS`, kept in sync with the CSS `transition-duration` by comment, not shared code — a minor duplication accepted for simplicity), calls the state-persisting `setNodeCollapsed`. The delay matters because that call triggers this view's usual full `render()` teardown-and-rebuild; doing it immediately would rebuild the DOM from scratch on the very next tick and cut the animation short with a hard snap instead of a slide.

**What's verified vs. not, for both:** the drop-target fix's actual reachability needs Dan's own drag input to confirm, same as everything drag-related in this build — I can't drag-test it myself. The icon alignment fix was verified directly via a zoomed live screenshot (Bets/To Do/Ideas icons now share one vertical line). The animation was verified to produce no console errors and correct end-states on toggle, but not that the motion itself looks smooth — that's inherently something only real eyes watching real motion can confirm, not something a static screenshot comparison can settle.

## F8: keyboard Delete unplaces without a confirmation step — deliberate, not an oversight

**Decision:** `handleRowKeydown`'s `Delete` case calls `unplaceUnit` immediately, with no `ConfirmModal` in between — unlike "Delete view" and "Delete meta folder," which do confirm first.

**Why no confirm here specifically (per review, A8/A9):** unplacing a unit isn't destructive under this model — the unit doesn't disappear, it just returns to the inbox (its own view, or the global one), fully recoverable with the same "Place in view…" flow used to place it in the first place. Nothing on disk changes and no data is lost. Both "Delete view" and "Delete meta folder" *do* confirm (`ConfirmModal`, `showMetaFolderMenu`) even though neither is destructive either in the same disk-safety sense — their placements/children survive (moved to the global inbox, or up one level). The distinguishing factor isn't destructiveness, it's blast radius: those two actions can reshuffle however many placements or children a view/meta-folder holds in one keystroke, where Delete-to-unplace only ever touches the one row under the cursor. A confirmation step earns its place when an action's effect is large or hard to visually verify after the fact, not merely when something is technically reversible; a single-row, single-target action doesn't clear that bar the way a whole-view or whole-folder action does.

**What this means for the spec's "Delete to remove (with confirm)" wording:** read as describing the general shape of a delete-like action in the explorer, not a literal requirement that this specific keyboard shortcut must always confirm — the shape holds (actions with meaningful blast radius confirm; a single-row unplace doesn't have one).

## F8: real bug fixed post-review (A6) — drop-onto-nested-unit escaped to bucket root

**Decision:** `handleDrop`'s branch for "dropped onto a unit node, not a meta folder" (the Part 4 edge case where dropping a unit onto another unit should insert it as a sibling right after the target) hardcoded `parentId = null` regardless of where the target unit actually lived in the tree. `indexInParent` already did the equivalent recursive search to find the right *index* within whatever array the target lives in; this branch just never did the analogous lookup for the right *parent*. Fixed by adding `parentIdOf` — a recursive search returning the id of the meta folder a node lives in, or `null` for the bucket root — and using its result instead of the hardcoded `null`.

**How this was caught:** code review (A6), not live testing — dropping a unit onto another unit that's nested inside a meta folder would incorrectly escape the dropped unit out to the bucket root instead of landing inside that same meta folder as a sibling. This is exactly the failure mode the drag-and-drop-untestable-in-this-container limitation was hiding: none of the non-drag equivalents used throughout this build to verify `placeUnit`/`unplaceUnit` (the "Place in view…" flow, the temporary debug command, "Remove from view") exercise this specific branch of `handleDrop`, because they all call `placeUnit` directly with an already-correct `parentId` rather than going through the target-node → parent-lookup logic this bug lived in. A reminder that "verified the underlying method works" and "verified the UI computes the right arguments to it" are different claims — this build's non-drag substitutes covered the former, not the latter, for this one code path.

**Not separately live-tested even now** — still blocked on the same environment limitation (no working synthetic drag in this container) — but it's now correct by code inspection rather than silently wrong underneath a passing-looking test suite. Real drag-and-drop testing (per A7's recommendation) is the one item in this build genuinely best left for Dan's own hands-on pass.

## F11: scale test — real bugs found and fixed, not just a passing benchmark

**Decision:** scripted 5,050 root-file units + 2,000 free blocks directly into the fixture vault (rather than a separate scratch vault — this vault is already a disposable Atlas-testing fixture, see the "pangyo" note elsewhere in this log) to reach 7,075 total units from a 75-unit baseline, then measured and fixed what broke rather than just confirming the AC's number.

**Two real performance bugs found, not hypothetical ones:**
1. `resolveRef` (`explorer-view.ts`) did `this.plugin.unitIndex.getUnits().find(...)` — an O(n) linear scan — for every row resolved, and the inbox resolves every unit on every render to filter/sort it. That's O(n²) per render. At 75 units this is invisible (5,625 comparisons); at 7,075 units it's ~50 million, easily enough to make the UI feel broken even though nothing was logically wrong. Fixed by building a `Map<string, Unit>` (`unitsByRefKey`) once per `render()` call and using it for O(1) lookups — turns the whole render into O(n).
2. Free-block display text was read fresh from disk (`getFreeBlockDisplayText`) on every single render pass for every free-block unit, even though F7 already built and vault-event-maintains a `FreeBlockTextCache` for exactly this text. `resolveUnit` now takes that cache as an optional parameter and serves from it first, falling back to a fresh read only on a cache miss. `main.ts`'s `freeBlockTextCache` field was made public so the explorer could reach it.

**The virtualization design (inbox only, not the bucket):** the inbox renders inside a bounded, independently-scrollable viewport (`max-height: 45vh`) with fixed-row-height windowing — only the rows within the scrolled range (+ overscan) are ever real DOM nodes, positioned via `top` offset inside a full-height spacer so the scrollbar reflects the true list length. Redraws are `requestAnimationFrame`-throttled on the viewport's own `scroll` event, not routed through the view's full `render()` (which would re-resolve/re-sort/re-render the toolbar and bucket on every scroll tick). The bucket tree is left un-virtualized: it's user-curated, not vault-sized, and giving it its own bounded viewport too would be solving a problem it doesn't have. **Named scope boundary:** expanding a folder-unit's internals (F3) needs normal variable-height document flow, which the fixed-row-height virtualized path can't represent, so virtualization is skipped entirely for that render pass when any folder is expanded. That's a deliberate, occasional-and-bounded fallback (one folder's contents, not the whole vault), not a gap in the thousands-of-rows case that actually needs protecting.

**Fixed row height is an assumption, not a measurement:** `INBOX_ROW_HEIGHT = 28` is a constant, not measured from the real rendered DOM. All inbox rows are single-line (`white-space: nowrap`, no wrapping content), so this holds in practice, but it's worth naming as a simplification rather than pretending it's derived.

**A real, scale-independent bug found along the way, not a scale-specific one:** the filter box lost keyboard focus after every keystroke, at *any* list size — `render()` empties and rebuilds the entire container, including the filter `<input>` itself, on every change (index update, view switch, *or* a filter keystroke, since typing calls `void this.render()` the same as everything else). The freshly-created input has no focus, so every keystroke past the first was silently discarded — this had been true since F8 shipped, just easy to miss with small lists where a one-character filter often still "worked" well enough to look intentional. Fixed by capturing `document.activeElement` and the filter input's caret position before `container.empty()`, and restoring both on the new input afterward.

**Environment finding, recorded so it isn't mistaken for an Atlas bug in a future scale test:** bulk-creating thousands of files directly on the host filesystem while the container's Obsidian instance is running does not reliably reach Obsidian's own vault index via this Docker bind mount's file watcher — repeated `Atlas: Rebuild index` runs under-counted for over a minute after file generation had finished on disk (175 → 286 → 1253 → 3120 → 4625, then stalled well short of 7,075). A `Reload app without saving` (forcing Obsidian's real startup-time full vault scan) picked up every file correctly on the first try. Atlas's index is only ever as complete as `app.vault.getFiles()` reports; if Obsidian's own watcher hasn't caught up, no amount of correct `create`/`delete` event handling in Atlas can compensate. Same class of issue as the earlier-documented external-rename-not-firing gap — a Docker bind-mount file-watching limitation, not something a real (non-containerized) install would hit.

**The actual numbers, for the record:** `[Atlas] full index rebuild in 18.0ms (7075 units)` (`{"folder-unit":24,"root-file":5050,"free-block":2000,"promoted-file":1}`), incremental promotion recompute consistently 4.5–6ms per event (1636 links scanned) throughout. Both comfortably clear the spec's "<2s full rebuild, <100ms incremental" bar at scale — F2's original measurements (2.6–13ms full rebuild at 75 units) hadn't actually been checked against a vault big enough for the target to be meaningful until now.

**Cleanup:** all 7,075 scratch files were deleted after measuring, confirmed via `git status` (clean) and a rebuilt index matching the exact pre-test 75-unit baseline (`{"folder-unit":24,"root-file":50,"promoted-file":1}`, byte-for-byte the same breakdown).

## F8: temporary debug drag-placement command removed at PR close

**Decision:** the "Debug — place first inbox unit into bucket root" command (added mid-build to verify `placeUnit`'s state management independent of the untestable drag gesture) is removed from `main.ts` now that this PR is closing. It isn't in F10's finalized command list, and its job — proving `placeUnit`/`moveNode`/`unplaceUnit` work correctly — is now covered by non-drag equivalents that are staying: the "Place in view…" context-menu/command-palette flow (`placeUnit`), "Remove from view" (`unplaceUnit`), and view deletion moving orphaned placements to the inbox (also `unplaceUnit`, at a different call site).

**Why remove rather than keep it as a permanent hidden feature:** it was explicitly scoped as temporary when added (see the code comment it shipped with), the native drag-and-drop limitation it worked around is an environment/testing gap rather than something the shipped plugin needs a workaround for, and leaving an unlisted "Debug —" command in a real user's command palette is the kind of rough edge Part 7's "no disk-shape leaks in the UI" spirit argues against even though it's not literally a disk-shape issue — it's internal-testing scaffolding, not a feature.

## F8: Menu has no submenu API — "Place in view ▸" is a two-step modal flow instead

**Decision:** Obsidian's `Menu`/`MenuItem` API (confirmed by grepping `obsidian.d.ts`) has no way to attach a submenu to a menu item. The hand-off doc's "Place in view ▸" context-menu item is implemented instead as: click "Place in view…" → `ViewSuggestModal` (fuzzy-pick the target view) → `MetaFolderSuggestModal` (fuzzy-pick "(bucket root)" or a named meta folder within that view) → `viewsManager.placeUnit(...)`.

**Why not something else:** a flat single-level menu listing every `view › meta-folder` combination was considered and rejected — it doesn't scale (grows with views × meta folders) and reads worse than two short, focused picks. The two-modal flow also reuses the exact same `ViewSuggestModal`/`MetaFolderSuggestModal` classes that F10's `place-active-file-in-view` command already needed, so it isn't one-off scaffolding.

**Verified live, full round-trip:** right-click a unit in the inbox → "Place in view…" → picked "Weekly" → picked the "Ideas" meta folder → the unit (`opencode.jsonc`) appeared correctly nested under "Ideas" in Weekly's bucket, and the inbox count dropped by one. Also used from the command palette (`Atlas: Place active file in view…`) with the same two-step flow, confirming both entry points share the same code path.

## F8/F9: modal and menu button clicks — real coordinates fix what earlier looked like an environment bug

**Decision:** no code change. The PR-4-in-progress note (now corrected) claimed `TextPromptModal`/`ConfirmModal` OK/Cancel buttons were unreliable to click via synthetic X11 input, with keyboard-only interaction as the only proven path. Retested this pass with pixel-precise coordinates (cropped + 4x-upscaled screenshots of the exact button before clicking, rather than eyeballing coordinates from a full screenshot) and both button types clicked correctly and repeatedly: `ConfirmModal`'s red "Delete" button (used twice, once per view-deletion test) and `Menu`'s "Place in view…" item (used twice).

**Why the earlier finding was wrong:** the full-window screenshots returned by this container are rendered at 2056×1178 but displayed to the assistant at 2000×1146 — a ~2.8% scale difference easy to miss when reading pixel coordinates directly off the displayed image. At a 24–30px button height, that error is enough to land clicks one row off or on a button's edge. Cropping the exact control at native resolution before clicking removes the ambiguity. Keyboard-driven interaction (typing right after a modal opens, Enter to submit) remains a fine fallback and was kept as the primary path for `TextPromptModal` text entry throughout this pass — this finding is specifically about *button clicks*, not a reason to distrust the keyboard path.

## F9: rewriteRefPath's rename handling verified live — with one real environment caveat surfaced along the way

**Decision:** no code change; the existing `vault.on('rename')` handler (`unitIndex.onVaultRename` + `viewsManager.onVaultRename`) is correct as built. Verified live by placing a file, renaming it via Obsidian's own in-app rename (command palette → "Rename file", which edits the note's inline H1 title and calls `vault.rename` under the hood), and confirming `data.json`'s `ViewNode.ref.path` updated to the new filename while the node's `id` and position in the tree stayed identical.

**The caveat, surfaced by accident and worth recording precisely:** an *external* rename performed directly on the host filesystem (`mv` from outside Obsidian, while the container's Obsidian instance is running against the same bind-mounted vault) did **not** fire Obsidian's `rename` event — instead it was reported as a delete of the old path (the placement correctly rendered as a greyed "(missing)" row, per spec) with no corresponding pickup of the new file into the same ref. This is a Docker bind-mount file-watching limitation (the same class of issue as the earlier documented native-drag-and-drop gap), not an Atlas defect: Atlas only ever reacts to whatever `rename` event Obsidian itself decides to fire, and Obsidian's own file watcher didn't correlate the unlink+create into a rename over this mount. A real user renaming a file from their OS's file manager on a native (non-Docker-bind-mounted) install would not hit this. Recorded here so it isn't mistaken for an Atlas bug if it resurfaces in future container testing.

**Side effect caught and reverted, not left in the vault:** testing folder-level rename (`Bets` → `Bets Renamed` → `Bets`, both via Obsidian's own native-explorer rename, to exercise the prefix-rewrite branch of `rewriteRefPath` against a folder-unit) triggered Obsidian's own link-updating feature, which rewrote *relative* markdown-style links (e.g. `[steps/bets-sweep-family.md](steps/bets-sweep-family.md)`) in 8 files under `Bets/` incorrectly on the round trip, stripping the `steps/` prefix and leaving broken links. This is a pre-existing Obsidian behavior around relative (non-wikilink) markdown links during folder renames, entirely unrelated to Atlas's own code — Atlas never touches file content. Caught via `git status` immediately after, and reverted with `git checkout --` before doing anything else, so the vault's real content is untouched. Named here as a real, reproducible gotcha for any future container-based rename testing in this vault: prefer testing renames against files, not folders with internal relative-link cross-references, or be ready to check `git status` and revert immediately after.

## F9: inbox mode differential test — the two-view scenario needs a unit placed in only one view

**Decision:** to actually distinguish "This view" from "Global" inbox mode (not just click the toggle and eyeball a count that happens to be the same either way), the live test placed one unit (`Bets`) in *both* views' buckets and a second, different unit (`Content`) in only one view's bucket, then compared inbox counts across both modes and both active views.

**Why this mattered:** the first attempt at this AC placed the same single unit in both views' buckets, which meant "This view" and "Global" produced the identical count for both views (the unit was excluded from the inbox either way) — a passing-looking result that doesn't actually verify the mode distinction. Adding the second unit (placed in only one view) made the two modes diverge as expected: with "Weekly" active, "This view" mode showed 74 (only `Bets`, placed in Weekly, excluded) while "Global" mode showed 73 (`Bets` *and* `Content` excluded, since `Content` is placed somewhere even though not in Weekly). This is the actual shape of AC in Part 3/4 and is worth remembering as the template for testing this distinction again in the future.

## F8/F9 live verification pass — what's carried forward as a real gap vs. deferred by design

**Decision:** native HTML5 drag-and-drop (inbox → bucket, reorder within bucket, bucket → inbox) remains untestable via `xdotool`-driven synthetic X11 input in this container — reconfirmed this pass with careful multi-step `mousedown`/`mousemove`/`mouseup` sequences, same as the original finding during the initial F8 build. Every drag-driven state mutation (`placeUnit`, `moveNode`, `unplaceUnit`) was instead verified live through an equivalent non-drag path that calls the identical method: the temporary debug command, the "Place in view…" context-menu/command-palette flow, and the "Remove from view" context-menu action, respectively. `moveNode`'s reorder-specific logic (splice + circular-placement guard) has no non-drag equivalent and remains code-reviewed only, not live-exercised — named explicitly in TASKS.md rather than left ambiguous.

**Why ship without a code fix for the drag limitation:** this is a testing-environment gap, not a code defect — the drop handlers themselves are wired identically to how every other Obsidian community plugin implements drag-and-drop, and there's no indication real trackpad/mouse input in a real browser or Electron window would behave differently. Re-confirming this each time a new drag-dependent AC comes up (rather than assuming the first finding still holds) is deliberate — environment quirks are exactly the kind of thing that can silently resolve itself with a container/tooling update and shouldn't be trusted from one earlier data point indefinitely.

## F6: self-calibrating suggestion sort (post-PR-4 review A4, refined post-PR-5 review A5)

**Decision (final form):** a unit (`folder-unit`/`free-block`/`promoted-block`) only sorts above plain `file` matches when its own fuzzy-match score is at least as good as the best `file`-kind score in that same result set. Otherwise it's sorted by score alongside files, same as before. No fixed tier, no magic-number margin — the threshold is the query's own best file match, recomputed per query.

**How this evolved (two rounds, both driven by live evidence, not review-only back-and-forth):**
1. **A4** caught that "`[[bets` surfaces the `Bets` folder-unit" was checked off but not actually guaranteed — pure fuzzy-score sort meant a real competing file (e.g. `Bets/notes-on-bets.md`) could out-rank the folder-unit. First fix: an unconditional kind tier (all units always outrank all files). Verified live, closed the gap.
2. **A5** pushed back on that fix after seeing its own live evidence: the unconditional tier meant *any* unit, however weak its match, now outranked *every* file. Confirmed live: typing `bets` surfaced `Kubernetes` and `Objectives` — both incidental weak subsequence matches — above an exact-ish `bets` filename match. The reviewer judged this a bigger behavior change than the hand-off doc's two narrow examples called for, and asked for a margin/threshold instead, suggesting the self-calibrating form specifically to avoid picking an arbitrary constant.

**Why the self-calibrating form over a fixed margin:** a fixed threshold (e.g. "unit score must be within 10 points of the best file score") requires guessing a constant with no principled value, and would need re-tuning if Obsidian's fuzzy-search scoring ever changes. Comparing directly against the best file score in the same query's result set has no constant to pick and degrades sensibly (no files matched → every unit clears the bar trivially, since there's nothing to bury).

**Verified live, both directions, with the same fixture file (`Bets/notes-on-bets.md`) that exposed the original gap:** `Bets`/folder still sorts first (its match against "bets" is competitive with the best file match) — the case A4 cared about. `Kubernetes`/`Objectives` no longer outrank the exact `bets`/`Bets` file matches — the case A5 cared about. Both confirmed in the same test run, not assumed from the code alone.

## Fixed a real bug found via container testing: block-only links were also promoting their containing file

**Decision:** a link with a subpath (`[[file#^id]]` or `[[file#Heading]]`) now promotes only the block, never the file it lives in. Only a subpath-less reference (a bare `[[file]]` link or a whole-file embed) can promote the file/folder itself.

**Why:** the first implementation derived file/folder promotion from `metadataCache.resolvedLinks`, which collapses subpath links down to their target file — so a link to one paragraph was also promoting the whole containing note as a second, separate unit. Caught live in the container: created a throwaway `[[target#^id]]` link between two scratch files, and the target file showed up in both `promotedBlocks` *and* `promotedFiles`. Fixed by driving both file-level and block-level promotion off a single pass over each file's `cache.links`/`cache.embeds`/`cache.frontmatterLinks`, branching on whether the reference carries a subpath — `resolvedLinks` is no longer used at all. Also had to add `cache.frontmatterLinks` to that scan (missed on the first pass of the fix): a real promotion in the fixture vault (`_system/Classroom/Tutor/tutor-playbook.md`, linked from a `playbook: "[[tutor-playbook]]"` YAML property in `FDE Play/...`) briefly disappeared until that was added, since frontmatter-property links live in their own cache array, not `cache.links`.

## Dot-folders are invisible to Obsidian's vault API
